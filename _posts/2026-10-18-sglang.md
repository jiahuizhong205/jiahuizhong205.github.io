继 vLLM 之后，这次读的是 [SGLang: Efficient Execution of Structured Language Model Programs](https://arxiv.org/abs/2312.07104v2)。上一篇主要在理解 KV Cache 怎样被分页管理，SGLang则讨论：一个程序包含多次 LLM 调用时，能不能利用这些调用之间的关系，减少重复计算、提高执行效率？

读这篇论文的过程中，我也顺手补了几个之前没有完全理清的概念：SGLang 和 vLLM 分别处于哪一层，批次、请求、prompt 和 token 又是什么关系。这里按自己的理解整理一下。

## 一、SGLang 和 LM program 是什么

SGLang 是一个用于高效执行复杂语言模型程序（LM program）的系统，由一套前端语言和一个运行时系统组成。

- 前端负责表达“要执行哪些模型调用，以及调用之间有什么关系”。
- 运行时负责把这些操作实际执行出来，包括调度、缓存和 GPU 计算。

LM program 可以理解为：**利用程序来调度和控制 LLM 的生成过程。**论文提到的高级提示技术和 Agent 工作流都属于这个范畴。

它通常具有两个共同特征：一是包含多次 LLM 调用，调用之间穿插控制流；二是接收结构化输入，并产生结构化输出。结合 Agent 工作流就比较容易理解：先让模型判断是否需要调用工具，再获取外部信息，可能还要并行分析几份材料，最后把结果整理成指定格式，交给下一个程序继续使用。

论文提出了两个主要难点。首先，LLM 输出具有非确定性，程序往往需要处理大量字符串操作、提示词调整和容易失效的输出解析，还要自己控制并行流程。其次，多次调用之间可能存在重复内容，如果每次都重新计算、各存一份，就会产生冗余计算和内存占用。

SGLang 的名字来自 Structured Generation Language，也就是面向 LLM 的结构化生成语言。其核心思想是：**系统地利用语言模型程序中的多次调用结构，实现高效执行。**

前端是一种嵌入 Python 的领域专用语言，可以和 Python 的控制流、库一起使用，并提供 `gen`、`select`、`fork`、`join` 等原语。后端则提出了几项优化：用于 KV Cache 前缀复用的 RadixAttention、加速结构化输出的压缩有限状态机，以及面向黑盒 API 模型的 API 推测执行。

## 二、SGLang 和 vLLM 分别在哪一层

论文把面向 LLM 的编程系统分为高层系统和低层系统。LangChain、DSPy 属于前者，LMQL、Guidance 和 SGLang 属于后者。

区别主要在抽象层次：高层系统可以提供预先定义或自动生成的提示词，低层系统则允许用户直接操作提示词和原语。层次不同，它们可以同时存在，例如 SGLang 可以被集成到 DSPy 中作为后端。

我的直观理解是：高层系统负责组织任务、构造或优化提示词；SGLang 这一层负责表达具体操作，并高效执行。

读到这里，我问了 GPT：**那 vLLM 属于哪一层？**这个回答帮我把两种分类区分开了：论文这里说的“高层、低层”，主要是在比较编写 LLM 程序的系统；vLLM 主要负责执行模型推理，并不是像 SGLang 前端那样的一套编程语言。

可以按职责整理成下面的表格：

| 层次 | 主要职责 | 例子 |
|---|---|---|
| 应用编排层 | 组织任务、工具调用，构造或优化提示词 | LangChain、DSPy |
| 程序表达层 | 表达生成、选择、分支、同步等操作 | SGLang 前端、LMQL、Guidance |
| 推理执行层 | 执行 prefill/decode，管理 KV Cache、批处理和 GPU 资源 | vLLM、SGLang Runtime |

![SGLang 与 vLLM 在不同职责层次中的位置](/assets/img/posts/2026-10-18-sglang/01-system-layers.png)

_图 1：按职责理解系统层次。示意图由 GPT 根据论文与本文笔记绘制；各层不是每次调用都必须经过的固定流水线。_

所以，vLLM 与 SGLang Runtime 的比较，主要落在推理执行这一侧；SGLang 前端与 LMQL、Guidance 的比较，主要涉及程序表达与控制能力。完整的 SGLang 同时包含前端和运行时，还会利用两者的协同进行优化。

## 三、RadixAttention：把前缀对应的 KV 留下来

接下来，论文详细介绍了后端的几个机制。首先是 RadixAttention，它能够在运行时自动、系统性地复用 KV Cache。

同一个程序可能分出多个并行分支，不同程序实例也可能共享系统提示词。对同一模型和相同推理配置来说，如果请求具有相同的 token 前缀，这一部分的 KV 就可以复用。例如：

```text
请求 A：[系统提示词][同一份文档][问题 A]
请求 B：[系统提示词][同一份文档][问题 B]
        └──── 可以共享的前缀 ────┘
```

RadixAttention 会保留已经计算好的提示词及生成结果对应的 KV，用一棵 radix tree（压缩前缀树）管理 token 序列与 KV Cache 的映射。树的索引结构保存在 CPU 上，实际 KV 张量采用 GPU 上的非连续分页布局。

论文说，它把 KV Cache 像传统缓存一样管理（唔，炒冷饭的感觉）前缀树、LRU，这些工具本身都很熟悉。继续往下看，它的工作不只是换个数据结构，也把动态的多层前缀共享、缓存淘汰、调度，以及前端提供的信息一起组织起来。

比如，新请求在一条已有路径中间发生分叉时，就可以把原来的长边拆开，让两个分支共享前面的部分。显存不够时，优先淘汰最近最少使用的叶节点，尽量保留仍能被其他分支共享的祖先；正在被运行中请求使用的节点，则通过引用计数保护起来。

![RadixAttention 的前缀共享、节点拆分与 LRU 淘汰](/assets/img/posts/2026-10-18-sglang/04-radixattention-paper.png)

_图 2：RadixAttention 随请求到来而动态变化。绿色表示新增节点，蓝色表示当前访问到的已有缓存节点，红色表示淘汰节点。图源：SGLang 论文 Figure 3，仅裁去图注和页边空白。_

缓存和运行中的请求共享同一个显存池，而不是预先给历史缓存划出固定容量。新的请求需要空间时，可以回收当前没有请求使用的缓存。

这些机制与连续批处理、PagedAttention、张量并行等技术兼容。

### 1. 宕开一笔：批次、请求、prompt 和 token

读到连续批处理时，我发现自己对“批次、请求、prompt、token”之间的关系还没有完全理清，正好在这里记下来。

先考虑文本输入、每个请求生成一份回答的情况：

- **请求（Request）**：一次生成任务，包含输入和生成设置。一个 Agent 程序可以发出多个请求。
- **Prompt**：这个请求的输入上下文，可以包括系统提示词、历史对话和当前问题。
- **Token**：模型处理文本的基本单位，既存在于输入 prompt 中，也存在于生成的回答中。
- **批次（Batch）**：本轮一起参与计算的一组请求。

![批次、请求、prompt 与 token 的关系](/assets/img/posts/2026-10-18-sglang/02-request-prompt-token.png)

_图 3：请求包含输入与生成任务，输入和输出都由 token 构成。Batch 是执行时组织的请求集合，成员可以变化。示意图由 GPT 绘制。_

这里最容易混淆的有两点。第一，batch size 是请求数量，不是 token 数量；同一批请求的 prompt 和回答长度可以不同。第二，上一轮的模型回答，在下一轮会成为输入 prompt 的一部分，因此输出 token 也可能在后续请求中成为输入 token。

### 2. 连续批处理：不必等整批请求全部结束

**连续批处理（Continuous Batching）就是：在每轮模型计算之间调整批次，让完成的请求退出，让等待中的请求加入，不必等整批请求全部结束。**这种迭代级调度机制可以参考 [Orca 论文](https://www.usenix.org/conference/osdi22/presentation/yu)。

假设一个批次最初包含 A、B、C 三个请求，A 只需要生成 2 个 token，B 需要 5 个，C 需要 3 个。A 完成后，系统就可以在后续迭代中加入 D，而不用等 B、C 都完成；之后 C 完成，又可以加入 E。

![连续批处理中请求随生成迭代动态加入和退出](/assets/img/posts/2026-10-18-sglang/03-continuous-batching.png)

_图 4：每轮最多推进三个请求，完成的请求退出后，新请求可以加入。这里只展示 decode 调度，新请求的 prefill 和具体资源预算已省略。示意图由 GPT 绘制。_

### 3. 缓存感知调度：有机会加入批次时，优先选谁

连续批处理说明了批次可以怎样变化；缓存感知调度进一步考虑，等待队列中有多个请求时，先处理哪一个。

因为系统既会复用缓存，也会淘汰缓存，如果总在互不相关的请求之间切换，就可能刚删掉一段缓存，后面又需要重新计算。让共享前缀的请求尽量连续处理，就能减少这种反复淘汰和重算。

论文采用的是“最长已匹配前缀优先”：优先考虑能够复用更长已有缓存前缀的请求。这里的“相关”具体指 token 前缀匹配，不是语义上讨论了相似的问题。理解到这一层，调度的动机就比较直观了。

论文还在离线场景和一定缓存容量条件下，证明了深度优先遍历能够达到最优缓存命中率。不过在线服务中还会有新请求到达，而且一味优先处理高命中请求可能让其他请求长期等待，所以实际调度也要考虑公平性。

### 4. 现在的 vLLM 也有前缀复用

读完这里，我还追问了一下：vLLM 现在是不是也有类似机制？答案是有，官方称为 [Automatic Prefix Caching（APC）](https://docs.vllm.ai/en/stable/features/automatic_prefix_caching/)。它同样可以复用公共前缀对应的 KV，主要减少重复的 prefill 工作。

按 2026 年 10 月查阅的[官方设计文档](https://docs.vllm.ai/en/stable/design/prefix_caching/)，vLLM 主要使用基于哈希的 KV block 索引：哈希包含前一个块的哈希、本块 token 和必要的额外标识。论文中的 RadixAttention 则使用压缩前缀树组织这些共享关系。

另外，这篇 SGLang 论文的实验基线是 vLLM v0.2.5；论文脚注也已经提到，当时更新的 vLLM 中已部分集成相关能力，作为可选实验功能。因此，论文中的对比要放回当时的版本和配置来看。

## 四、压缩有限状态机：固定内容可以一起处理

后面是压缩有限状态机，用来加快结构化输出的约束解码。这一节内容不多，还配了一张图。

我一开始不太理解，后来把输出分成“格式已经确定的内容”和“需要模型判断的内容”，就容易接受了。例如：

```text
{"grade": " → A 或 B → "}
└── 固定 ──┘  └判断┘  └固定┘
```

如果格式要求输出 `grade` 字段，而且评分只能是 A 或 B，那么字段名、冒号、引号等都是固定的，真正需要模型判断的是选择哪个评分。

普通约束解码把正则表达式转换成有限状态机，每一步根据当前状态屏蔽非法 token，再继续逐 token 解码。这样即便后续内容已经被格式完全确定，也仍然可能执行多次串行解码。

SGLang 分析状态机，把连续确定的转移合并成一条边。到达这种路径时，系统直接补入已知字符串，再把对应的多个 token 一起送入模型计算状态和 KV，然后继续生成需要判断的部分。

所以，我原先说的“固定 token 可以一次性生成多个”，更准确地说是：**固定片段可以直接补入，再一起计算对应的 KV，省去逐个决定这些 token 的步骤；不确定的内容，在普通自回归解码中仍然基本逐 token 生成。**

![普通有限状态机与压缩有限状态机的解码流程](/assets/img/posts/2026-10-18-sglang/05-compressed-fsm-paper.png)

_图 5：上半部分展示状态机的路径压缩，下半部分展示对应的模型执行流程。下划线表示空格。图源：SGLang 论文 Figure 4，仅裁去图注和页边空白。_

对着这张图再看，会更容易理解“把多步变成一步”是什么意思。状态机描述的是字符或字符串约束，模型处理的则是 token，一个字符不一定对应一个 token；论文在附录 B 中进一步讨论了重新分词等实现细节。

## 五、API 推测执行：让一次调用多做一点

第三项优化针对的是只能通过 API 访问的模型（点名OpenAI，Authropic）。调用方无法修改模型内部的推理过程，因此需要从 API 调用方式入手。

论文举了一个先生成姓名、再生成职业的例子。直接实现时，两次生成对应两次 API 调用，第二次还需要带上前面的上下文。

SGLang 可以在第一次调用时，允许模型越过原先的停止条件，多生成一些内容，并把额外输出暂存下来。如果这些内容恰好与后续操作的模板匹配，就可以复用，省去一次调用。

例如，原本只想先取得姓名 `Alice`，模型却已经顺着模板继续生成了 `job:Engineer`。当程序走到生成职业的操作时，如果匹配成功，就可以直接使用这部分结果。这里推测的是“提前生成的内容能不能被后续程序用上”，效果取决于模板匹配和提示词设计。


论文还用一个 SGLang 程序讲解了原语的使用，不详细讲了。

这篇论文我觉得重点是理解KV Cache的前缀复用，压缩有限状态机之前没有听说过，但是理解之后发现确实很合理，文章开篇的三层结构算是小小的科普了，理清了一些概念。
