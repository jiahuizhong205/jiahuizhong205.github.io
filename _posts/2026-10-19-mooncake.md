这次读的是 FAST 2025 的 [Mooncake: Trading More Storage for Less Computation — A KVCache-centric Architecture for Serving LLM Chatbot](https://www.usenix.org/conference/fast25/presentation/qin)。从标题来看，就是用更多存储换取更少计算，主要聚焦的对象是 KV Cache。

前面读 vLLM 和 SGLang 时，已经接触了分页管理和前缀复用。Mooncake 则把问题进一步放到 GPU 集群中：缓存不一定只留在当前 GPU 上，还可以组织成一个全局缓存池，再围绕缓存的位置和实例负载安排请求。

这篇笔记先记录架构、传输引擎和调度方面的理解，后面的实验没有再细看。

## 一、目标：在满足 SLO 的同时最大化有效吞吐量

Mooncake 的核心，是一个以 KV Cache 为中心的全局缓存，以及一个调度器。调度器的目标是在满足严格的延迟相关服务等级目标（SLO）的同时，最大化吞吐量。

论文将 Kimi 的服务目标描述为一个具有多种复杂约束的优化问题：最大化整体有效吞吐量，约束条件则体现不同层次的 SLO。这里明确关注两个性能指标：

| 指标 | 含义 | 用户的直观感受 |
|---|---|---|
| TTFT，Time to First Token | 从请求到达到生成第一个 token 的时间 | 多久开始回答 |
| TBT，Time Between Tokens | 同一请求相邻输出 token 之间的时间间隔 | 开始回答后，生成是否流畅 |

我原先把它们记作 benchmark，更准确地说，TTFT 和 TBT 是衡量性能的指标，SLO 则规定这些指标需要满足的要求，例如允许的延迟上限。

论文还提到 Goodput，也就是有效吞吐量。它关注的是**满足 SLO 的吞吐量**。普通吞吐量可能更高，但如果请求等待很久，或者生成过程很慢，单个用户的体验并不好，按服务目标衡量也未必算有效完成。

## 二、从 P/D 分离到以 KV Cache 为中心的资源池

为了充分利用 GPU 集群中的各种可用资源，论文认为有必要对高度集成的服务器资源进行解耦和重组，形成多个资源池。每个资源池针对不同、但相互协作的目标进行优化，最直接的例子就是 prefill 和 decode 分离。

在这个基础上，Mooncake 进一步组织 GPU 集群中的 CPU、DRAM、SSD 和 RDMA 资源，构建解耦式 KV Cache，称为 **Mooncake Store**。

论文把这称作高效的 near-GPU prefix caching。我对这里“近”的理解是：利用 GPU 服务器及其高速互连附近的存储资源共同保存缓存，缓存不必全部留在 GPU 显存中。其中，DRAM、SSD 提供存储容量，CPU 和 RDMA 等资源则参与管理、处理和传输。

![Mooncake 的整体架构](/assets/img/posts/2026-10-19-mooncake/01-mooncake-architecture.png)

_图 1：Mooncake 架构。上方是 prefill 池，下方是 decode 池，中间的 Mooncake Store 组织分布式 KV Cache；左侧 Conductor 负责全局调度。图源：论文 Figure 2，仅裁去图注和页边空白。_

用数据流理解这张图比较直接：

```text
已有 KV Cache
      ↓ 加载可复用部分
Prefill 实例：计算尚未缓存的部分
      ↓ 传输 KV Cache
Decode 实例：继续生成回答
```

两个阶段的优化重点不同。

**Prefill 阶段**主要希望尽可能复用 KV Cache，避免冗余计算。Conductor 需要感知缓存状态来调度请求，并相应安排换入换出、复制等操作。

**Decode 阶段**则希望在一个解码批次中聚合尽可能多的 token，提高模型浮点运算利用率（MFU），但不能超过显存容量，也不能让每轮生成时间违反 TBT 要求。

这里可以接上之前连续批处理的例子：多个请求各自的下一个 token 一起计算。一个 token 的隐藏向量乘权重矩阵，多个 token 一起就变成了矩阵乘矩阵。加载的权重块能服务于多个 token，数据读取成本得到分摊，算术强度和计算效率就有机会提高。这个收益主要体现在整体吞吐量上，单个请求的生成间隔未必缩短。

P/D 分离能够让两类计算分别优化，但也带来了 KV 传输开销，需要权衡。论文通过成本分析和实验说明，在其研究的硬件、网络与 SLO 条件下，这种组织方式能够带来收益。

## 三、搬过来，还是重新算一遍

第 2.2 节让我觉得比较有意思：它分析了需要多少带宽，全局缓存才有价值，说明缓存未必只能限制在本地 HBM 和 DRAM 中。

把公式背后的判断写出来，其实很直观：

$$
\underbrace{\frac{S_{\mathrm{KV}}}{B}}_{\text{加载缓存所需时间}}
<
\underbrace{\frac{\Delta C}{G}}_{\text{省下的重新计算时间}}
$$

其中，$S_{\mathrm{KV}}$ 是要加载的 KV 数据量，$B$ 是实际加载带宽，$\Delta C$ 是复用前缀能够省下的计算量，$G$ 是计算吞吐率。

也就是：**把缓存搬过来所花的时间，比自己重新算一遍更少，复用才会改善这里分析的 TTFT。**

这也解释了一个起初容易忽略的方向：对于同一个模型和相同前缀，如果 GPU 算得更快，重新计算所需的时间就会缩短；希望缓存复用继续占优势，传输也要足够快，所需带宽就会更大。

所以，“用存储换计算”不只是多准备一些空间。缓存容量决定能留下多少结果，实际传输带宽则决定这些结果能否及时用起来。这个公式是论文的近似成本分析，真实系统还需要考虑排队、调度以及计算和通信的重叠。

![Mooncake 中推理实例的工作流](/assets/img/posts/2026-10-19-mooncake/02-inference-workflow.png)

_图 2：推理实例工作流，包括 s1 前缀缓存复用、s2 增量 prefill、s3 KV 传输和 s4 解码。图源：论文 Figure 3，仅裁取右栏原图，未包含旁边的公式与正文。_

我刚看这张图时，感觉它和正常使用 KV Cache 的推理流程差别不大，最显眼的变化就是多了 s3，也就是 KV Cache 传输。

继续对照正文后，可以把区别理解得更具体一些：前缀 KV 可以来自远端 CPU 内存，prefill 和 decode 由不同实例完成，新产生的 KV 会按层流式传到目标 decode 节点，计算和传输还可以部分重叠。

因此，这里变化的是缓存的保存位置、复用范围和数据路径。对模型计算来说，仍然是在利用前缀 KV，补算缺少的部分，再继续生成；对服务系统来说，则需要把这些状态准确、及时地交给另一个实例。

## 五、Mooncake Store：缓存块管理与传输引擎

第三节介绍了系统的主要设计。除 prefill 节点池外，其中很大一部分内容都在讲 Mooncake Store。

所有 KV Cache 都以分页块的形式保存在分布式缓存池中，通常每块包含 16～512 个 token。块的标识同时包含本块和前缀的信息，用来识别相同的缓存内容；同一个逻辑块还可以在多个节点保存副本。空间不足时采用 LRU 淘汰，但正在被请求使用的块需要受到保护。

读到这里，我会自然联想到前面 vLLM 的分页管理，以及后来了解到的哈希式前缀缓存。这些机制确实能对应起来，不过分页、哈希和 LRU 都是通用工具，仅凭相似性还不能把它们直接归为“来自 vLLM 的方法”。这篇里更值得关注的是，它们如何被组织成分布式缓存，并与跨节点传输和全局调度配合。

具体的接口及使用方式这里就不展开了。我更想详细记一下传输引擎，因为之前对这一块了解比较少。论文主要讲了网络配置、拓扑感知路径选择、端点管理和故障处理。

![Mooncake Store 的传输引擎](/assets/img/posts/2026-10-19-mooncake/03-transfer-engine.png)

_图 3：左侧为批量传输接口，右侧为拓扑感知路径选择，展示 CPU、内存、GPU、网卡之间的连接关系以及首选和备用网卡列表。图源：论文 Figure 4，仅裁去图注和页边空白。_

### 1. 网络配置：高带宽还需要软件把它用起来

Mooncake 需要支持 CPU 内存之间的传输，也需要适应节点和网卡动态变化，并在部分路径失效时换路重试。这些需求推动了专门传输引擎的设计。

一台机器有多张高速网卡，并不意味着软件自然就能用满总带宽。引擎还要把传输任务合理分配给多张网卡，并管理连接和状态。

为了处理拥塞，论文同时采用了两类方法：网络侧使用由云服务提供商调优的 RoCEv2；调度侧增加热门 KV Cache 的副本，让多个节点共同承担读取压力。

### 2. 拓扑感知路径选择：机器内部也有远近之分

这个算法用来寻找更高效的传输路径。一台服务器可能有多个 CPU 插槽、多组内存、GPU 和 RDMA 网卡，它们在机器内部的连接并不完全相同。

例如，数据位于 CPU 0 所属内存，而选择的网卡连接在 CPU 1 一侧，数据可能需要额外经过 CPU 间互连。此时即使网卡本身很快，机器内部的路径也可能成为瓶颈。

Mooncake 为不同内存位置建立拓扑矩阵，列出首选网卡和备用网卡。正常情况下选更合适的路径，故障时再扩大候选范围。源端和目标端都要根据各自的内存位置选网卡。

此外，大传输会被继续拆成 16 KB 的小片，不同切片可以走不同路径，让多张 RDMA 网卡协同工作。这里的 16 KB 是传输切片粒度，与前面按 token 数量组织的 KV 缓存块是两个层次。

### 3. 端点管理：按需连接，并控制连接数量

这里的端点表示本地 RDMA 网卡和远端 RDMA 网卡之间的连接，内部包含一个或多个 RDMA 队列对，和调用模型服务的 HTTP API endpoint 不是同一个概念。

系统按需建立连接，并用端点池限制活跃连接数量，避免连接资源过多拖慢处理。端点淘汰使用 SIEVE；连接因链路错误失效后，会被移出两端的池，在下一次传输尝试时重建。

### 4. 故障处理：局部失败后寻找其他可达路径

多网卡环境下，一张网卡暂时不可用，不代表两个节点之间所有路径都不可用。Mooncake 会寻找替代路径，把传输重新提交给其他 RDMA 网卡，并暂时避开出现问题的 RDMA 资源。

端点管理和故障处理这里就先记到这个程度。对我来说，这部分补上的直觉是：多网卡既能提高聚合带宽，也能提供局部故障下的替代路径。

## 六、调度：谁拥有最多缓存，不一定谁最先完成

在 prefill 调度方面，系统综合考虑实例负载、前缀缓存命中长度，以及可复用 KV Cache 块的分布。拥有最长前缀缓存的实例如果很忙，把请求交给其他节点，反而可能更早得到第一个 token。

算法会估算请求在各个候选 prefill 实例上的 TTFT，再选择预计最快、能够满足约束的实例。其核心可以写成：

$$
\widehat{\mathrm{TTFT}}_i
=
\widehat T_{\mathrm{transfer},i}
+
\widehat T_{\mathrm{queue},i}
+
\widehat T_{\mathrm{prefill},i}
$$

我最初觉得这里有一点“仿真”的感觉（？）。更准确地说，prefill 计算时间由离线测试数据拟合出的多项式回归模型预测，输入包括请求长度和缓存命中长度；排队时间根据已有队列估算，传输时间还要考虑数据量和网络状态。然后调度器在线比较这些预测结果。

![缓存传输、排队与 prefill 时间共同决定预计 TTFT](/assets/img/posts/2026-10-19-mooncake/04-ttft-scheduling.png)

_图 4：调度器比较预计 TTFT 的直观示意。由 GPT 根据论文算法与本文笔记绘制，图中数值只用于解释，不是论文实验结果。_

算法还用一个前缀命中长度比例阈值，决定候选实例是否考虑获取远端缓存。如果远端优势不够大，就利用本地已有缓存计算剩余部分；最终选定实例后，还要检查 TTFT 和 decode 的 TBT 是否满足 SLO。

缓存分布也会随调度变化：热门缓存所在节点繁忙时，请求被分流到其他实例；后者取得缓存并在本地保留，后续请求就可能在那里命中。这样可以随着请求处理，逐步把热点副本扩散到更多实例，分散访问压力。

这里不展开完整伪代码。读下来更值得记住的是：调度比较的是包含传输、排队和计算的预计时间，而不只是命中长度，也不只是请求数量。
