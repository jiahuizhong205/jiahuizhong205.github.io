这次读的是 [Tutti: Making SSD-Backed KV Cache Practical for Long-Context LLM Serving](https://arxiv.org/abs/2605.03375)。前面读 Mooncake 时，关注的是如何把更多存储资源组织成全局 KV Cache；这篇则进一步关注，缓存放到 SSD 之后，怎样才能高效地搬回 GPU。

## 一、缓存放得下，还要搬得快

当希望保留的 KV Cache 超过 GPU HBM 和 CPU DRAM 的容量时，可以进一步卸载到 SSD。但容量变大之后，读取性能又成了问题。

问题的部分根源在于 vLLM、SGLang 等推理引擎采用的细粒度分页式 GPU 内存布局：逻辑上连续的 KV Cache，在显存中可能分散为许多小块。在论文讨论的存储映射和恢复方式下，把缓存搬回来会产生大量细小、随机的 I/O。如果每项 I/O 都需要 CPU 介入，逐项提交、同步和调度的开销就可能成为瓶颈。

前面读 Mooncake 时，已经知道边计算边传输可以隐藏一部分开销，当时对它使用的高速互连带宽也印象很深。不过，流水线里的每一段传输仍然需要足够高效。如果把传输切得更细，CPU 又要逐个提交 I/O，那么重叠带来的收益，就可能被额外的调度和小请求开销抵消。

## 二、从 CPU 发起 I/O，到 GPU 批量发起 I/O

论文提到了 GDS，即 GPUDirect Storage。它使 SSD 与 GPU 之间的数据传输能够绕过 CPU 内存中转，但在论文评估的 GDS 路径中，I/O 仍由 CPU 发起，所以 CPU 仍在关键的 I/O 控制路径上。

![CPU 驱动的缓存存储与 GPU 驱动的 Tutti 对比](/assets/img/posts/2026-10-22-tutti/01-tutti-architecture.png)

_图 1：左侧为 LMCache 不使用／使用 GDS 的路径，右侧为 Tutti。图源：论文 Figure 1，仅裁取原图，未修改图中内容。_

Tutti 是一种高效的 SSD KV Cache 方案，核心是一个以 GPU 为中心的 KV Cache 对象存储系统。图右侧看起来几乎不见 CPU，但实际上 CPU 仍然参与管理，并按层异步提交、启动 GPU I/O 内核；GPU 随后直接向 SSD 发出大量并行的 KV Cache 对象 I/O 请求。

这样，CPU 对细粒度 I/O 的控制开销就从 `O(layer × blocks)` 降到 `O(layer)`。这里减少的是 CPU 逐块控制的开销，并不是传输数据量变少了，也不意味着所有 CPU 工作都被移走。

## 三、直接发起 I/O 之后，还需要适配 KV Cache

论文归纳了三个挑战，并给出对应设计：

| 挑战 | 我的理解 | Tutti 的设计 |
|---|---|---|
| KV Cache 管理与存储抽象不匹配 | 管理什么：上层关心可复用的 KV 对象，底层提供的是文件或原始块 | GPU 原生对象抽象 |
| KV 传输与 GPU 存储 I/O 存在粒度差距 | 一次搬多少：KV 传输所需粒度与底层 I/O 粒度未必一致 | 异步 GPU io_uring，批量组织并发传输 |
| I/O 与模型计算竞争 GPU 资源 | 什么时候搬：I/O 控制内核也会占用 GPU 资源，可能干扰计算 | 感知资源空隙的 I/O 调度 |

我读下来的理解是：Tutti 把细粒度 I/O 的发起与处理交给 GPU，并让对象管理、传输粒度和调度方式适应 KV Cache。CPU 提前准备映射和批量任务，GPU 再按依赖关系执行；调度器利用资源空隙安排传输，减少对模型计算的干扰。

## 四、顺手理清 vLLM 与 LMCache 的关系

实验中，论文使用 LMCache 作为代表性的分层 KV Cache 系统，比较了 DRAM、SSD 和 GDS 等配置。性能指标除了 TTFT，还包括 ITL（Inter-Token Latency），也就是输出 token 之间的延迟，与上一篇 Mooncake 的 TBT 对应着理解。

这里我一开始有点混淆：LMCache 是不是 vLLM 的一个组件？更准确地说，**vLLM 自带 KV Cache 管理系统，LMCache 是可以通过 KVConnector 接入的独立缓存系统。**

vLLM 本身负责 KV 块的分配、回收、共享、前缀匹配和淘汰；接入 LMCache 后，这些管理工作仍然存在。LMCache 则提供分层存储、卸载与加载，以及跨请求、跨实例复用等能力。所以，“vLLM + LMCache”可以理解为推理引擎搭配一个外部缓存系统。

不过，两者的能力也有重叠：现在 vLLM 自身也提供原生 KV 卸载机制，不能简单理解为“vLLM 只管显存，显存之外一定要靠 LMCache”。读论文时，还是要结合它实际使用的软件版本和配置来看。
